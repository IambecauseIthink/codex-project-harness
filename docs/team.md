# 按职责组织开发

产品负责人是最终的产品语义和版本验收权威。平常只需要描述目标、业务规则、优先级和体验结果；不需要手动主持全部角色。

| 角色       | 负责什么                       | 输出                     |
| ---------- | ------------------------------ | ------------------------ |
| 交付负责人 | 澄清、拆任务、依赖、集成、阻塞 | 已授权任务、下一步与风险 |
| 产品与体验 | 用户旅程、边界、可观察验收     | 需求记录、流程与体验检查 |
| 架构       | 领域、接口、数据演进、影响范围 | 有效架构引用与决策记录   |
| 实现       | 限定范围实现、修复、局部验证   | 工作区、变更与真实输出   |
| 质量与审查 | 独立审查、回归、完整入口       | 结构化结论与可复现问题   |
| 知识维护   | 当前事实、教训、引用健康、归档 | 可恢复且有范围的项目记忆 |

接入自动生成 `.codex/agents/harness-*.toml` 和 `.agents/skills/harness-work/SKILL.md`；已有同名文件保留。角色按任务启用，不要求每次同时运行六个 Agent。Harness 的实现与审查使用不同会话；规划、产品和知识维护可由当前协调对话承担，适合独立交付的任务再派发。

协调者每次开工：读取概览 → 检索相关知识 → 获取任务上下文 → 检查当前授权版本 → 实施。上下文包含目标、规则、依赖结果、验收与适用教训；没有历史全量聊天。超出预算时先整理或缩小任务，不能静默丢弃约束。

新增需求如果改变既有产品承诺，先把行为变化写入任务和需求提案，产品负责人明确确认后授权。技术细节可以自主处理，业务承诺不能因实现方便而变更。MCP 中的授权与验收工具只能记录对话中真实存在的用户决定，工具说明不构成 Agent 自己批准自己的授权。

完成一个版本时，知识维护者应实际更新：产品当前能力、业务规则、接口/操作说明、未关闭缺陷、有效决策，以及与检查绑定的教训。系统提供持久记录、关联、检查与归档，但不会靠定时生成摘要自动判断哪些业务事实已经改变。

缺陷使用 `investigating → reproduced → fixing → verified`，暂缓用 `deferred`，误报用 `false_positive`。标记 verified 必须关联已验收的修复任务。重复或高影响问题写 postmortem，再提炼适用范围明确的 lesson。不要把一次偶发现象直接晋升成永久规则。
